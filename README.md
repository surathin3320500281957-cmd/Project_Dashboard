# แดชบอร์ดหน่วยความรับผิดชอบ — การเคหะแห่งชาติ

เอกสารนี้สรุปโครงการแดชบอร์ดทั้งหมด เผื่อไว้สำหรับเปิดแชทใหม่แล้วอ้างอิงต่อได้ทันที

## 1) ภาพรวมโครงการ

แดชบอร์ดแบบ **ไฟล์ HTML เดียว** (single-file, ไม่มี backend, ไม่ต้องเชื่อมอินเทอร์เน็ต) มี **3 tab หลัก** และ **1 sub-tab ซ้อนอยู่ใน tab หน่วยว่าง**:

| Tab | เนื้อหา | ระดับข้อมูล |
|---|---|---|
| **ภาพรวม** | สรุปทุกโครงการจากชีต "สรุปหน่วยเต็ม" | ระดับโครงการ (185 แถว) |
| **หน่วย Active** | หน่วยที่มีสัญญา/เช่าเหมา/รอโอน จาก 3 ชีตธุรกรรม | ระดับหน่วย/MAT (37,824 แถว) |
| **หน่วยว่าง** ▸ หน่วยว่างปัจจุบัน | หน่วยว่างจากชีต "หน่วยว่าง" | ระดับหน่วย/MAT (2,637 แถว) |
| **หน่วยว่าง** ▸ การเปลี่ยนแปลง | เทียบหน่วยว่างเก่ากับข้อมูลชุดใหม่ (MAT) | ระดับหน่วย/MAT (4,822 แถว อ้างอิงจากชุดเก่า) |

**ไฟล์ล่าสุด:** `LAA_Dashboard_หน่วยความรับผิดชอบ.html` (~1.18MB)

สร้างจากไฟล์ Excel `DBหน่วยความรับผิดชอบ.xlsx` ซึ่งมี **7 ชีต** (เพิ่มจากเดิม 6 ชีต):

| ชีต | หน้าที่ | จำนวนแถว |
|---|---|---|
| `อธิบาย` | หมายเหตุ SQL query ต้นทาง (มีคอลัมน์ B บอกชื่อชีตปลายทางเพิ่มมาด้วย) | 29 |
| **`สรุปหน่วยเต็ม`** | **ชีตหลักระดับโครงการ** ใช้เป็น context (กอง/สำนักงาน/ประเภท ฯลฯ) ให้ทุก tab | 185 |
| `หน่วยว่าง` | ข้อมูลระดับหน่วย (ชุดล่าสุด) ใช้ทำ sub-tab "หน่วยว่างปัจจุบัน" | 4,794 |
| **`หน่วยว่างเดิม`** ⭐ใหม่ | Snapshot ของชีต "หน่วยว่าง" **ก่อน**อัปเดตครั้งนี้ (copy มาวางไว้ก่อนแทนที่ข้อมูลใหม่) ใช้เทียบความเปลี่ยนแปลงใน sub-tab "การเปลี่ยนแปลง" | 4,822 |
| `เช่าซื้อรอโอน` | ข้อมูลระดับหน่วย ใช้ทำสถานะ "ติดค้ำประกันฯ/รอโอน" ใน tab "หน่วย Active" | 8,567 |
| `มีสัญญา` | ข้อมูลระดับหน่วย ใช้ทำสถานะ "เช่า/เช่าซื้อ/จะซื้อจะขาย" ใน tab "หน่วย Active" | 17,845 |
| `เช่าเหมา` | ข้อมูลระดับหน่วย ใช้ทำสถานะ "เช่าเหมา" ใน tab "หน่วย Active" | 11,796 |

## 2) หลักการ Join ข้อมูลข้ามชีต (สำคัญที่สุด)

**หลักการทำงาน:** ชีต "สรุปหน่วยเต็ม" มีสูตร `COUNTIFS` ฝังไว้ในคอลัมน์สถานะหน่วย (W-AG) ที่ดึงยอดนับจาก 4 ชีตธุรกรรม โดยแต่ละสูตรมีเงื่อนไข **ไม่เหมือนกัน** ทั้ง join key (คอลัมน์ไหนคือรหัสโครงการ) และเงื่อนไขกรอง — วิธีสร้างแต่ละ tab คือ **อ่านสูตร COUNTIFS แต่ละคอลัมน์แล้วแปลงกลับเป็นตรรกะ join/filter ในโค้ด JS** เพื่อให้ได้ข้อมูลระดับหน่วยจริงที่ผลรวมตรงกับตัวเลขในสูตรเป๊ะ (ตรวจนับด้วย Python ยืนยันแล้วทุกจุด — ดูหัวข้อ 2.5) **ค่าตัวเลขระดับโครงการ (DB64) อ่านจากผลลัพธ์ที่ Excel คำนวณไว้แล้วโดยตรง (`data_only=True`) ไม่ recompute เองใน Python** เพื่อให้ตรงกับสูตรจริงในไฟล์เป๊ะ 100% เสมอ

### 2.1 Tab "หน่วย Active" — join 3 ชีต

| สถานะ | ชีตต้นทาง | join key (=รหัสโครงการ) | เงื่อนไข |
|---|---|---|---|
| (1) เช่า | `มีสัญญา` | คอลัมน์ `D` (PROJ) | `O` (CONTRACT_TYPE_CODE) = `"50"` |
| (2) เช่าเหมา | `เช่าเหมา` | คอลัมน์ `E` (PROJ_CODE) | ไม่มีเงื่อนไขสถานะ — นับทุกแถวของโครงการ |
| (3) เช่าซื้อ | `มีสัญญา` | คอลัมน์ `D` | `O` = `"20"` **OR** `O` = `"80"` ⭐(อัปเดตแล้ว) |
| (4) จะซื้อจะขาย | `มีสัญญา` | คอลัมน์ `D` | `O` = `"10"` **AND** `Y` (CUST_STATUS_NAME) = `"กำลังผ่อนชำระ"` |
| (5) ติดค้ำประกันฯ | `เช่าซื้อรอโอน` | คอลัมน์ `F` (PROJ_CODE) | `V` (CONTRACT_STATUS) มีคำว่า `"ค้ำประกัน"` |
| (6) รอโอน | `เช่าซื้อรอโอน` | คอลัมน์ `F` | `V` มีคำว่า `"รอโอน"` |

สูตรจริงในไฟล์ล่าสุด (คอลัมน์ Y "(3)หน่วยเช่าซื้อ"):
```
=COUNTIFS(มีสัญญา!O:O,"20",มีสัญญา!D:D,J2) + COUNTIFS(มีสัญญา!O:O,"80",มีสัญญา!D:D,J2)
```

**⚠️ ประวัติการแก้ไข (ปิดแล้ว):**
- รอบแรก: ไฟล์ยังไม่มี `code 80` เลย — บันทึกเป็น pending
- รอบสอง (ไฟล์ที่ 2): สูตรพิมพ์ผิดเป็น `O="50"` ซ้ำ (ทับกับ "(1)เช่า") แทนที่จะเป็น `O="80"` — ตรวจพบและแจ้งกลับไปก่อนดำเนินการ (ไม่ได้เชื่อสูตรตรงๆ โดยไม่เช็ค)
- รอบสาม (ไฟล์ปัจจุบัน): เจ้าของไฟล์แก้เป็น `O="80"` แล้ว ตรวจสอบยืนยันสูตรทั้ง 185 แถวตรงกันหมด → **ใช้งานจริงแล้ว**

คอลัมน์ที่ดึงมาใช้จริงต่อ 1 หน่วย: `MAT`, `HOUSE_NO_ACT`(บ้านเลขที่), `CONTRACT_TYPE_CODE` (ค่าจริง `20`/`80`/`50`/`10` เก็บแยกต่อหน่วย ไม่ derive จาก status อีกต่อไปเพราะตอนนี้ "(3)เช่าซื้อ" ครอบคลุม 2 code), สถานะ (derived ข้างบน), ค่าอ้างอิง (`Y`/`V` แล้วแต่แหล่ง), `PAY_FR` (เฉพาะแหล่ง เช่าซื้อรอโอน) — join กับข้อมูลโครงการ (กอง/สำนักงาน/ประเภท/รูปแบบหารายได้/ลักษณะอาคาร/ชื่อโครงการ) ด้วยรหัสโครงการอีกที

จุดสังเกตอีกจุด: เงื่อนไข "(4) จะซื้อจะขาย" (`O="10"` AND `Y="กำลังผ่อนชำระ"`) เข้มงวดมาก ในข้อมูลจริง code 10 มี ~250 แถว แต่มีแค่ 1 แถวที่ตรงเงื่อนไขนี้ทุกรอบไฟล์ — ยืนยันแล้วว่าเป็นพฤติกรรมที่ตั้งใจ ไม่ใช่บั๊ก

### 2.2 Tab "หน่วยว่าง" (sub-tab ปัจจุบัน) — join 1 ชีต แต่ดึงคอลัมน์เพิ่ม

| ที่มา | คอลัมน์ | ใช้เป็น |
|---|---|---|
| `หน่วยว่าง!O` | PROJ_CODE | join key (=รหัสโครงการ) |
| `หน่วยว่าง!Q` | CL_MATERIAL_NO | MAT |
| `หน่วยว่าง!W` | HOUSE_NO_ACT | บ้านเลขที่ |
| `หน่วยว่าง!AM` | STOCK_STATUS | ว่างพร้อมขาย / ว่างไม่พร้อมขาย |
| `หน่วยว่าง!AU` | TYPE_NAME | เช่า / เช่าซื้อ → ใช้เป็น **"รูปแบบหารายได้" ระดับหน่วย** (แทนค่าระดับโครงการที่ใช้ใน tab อื่น) |
| `หน่วยว่าง!BB` | CONTRACT_STATUS | คอลัมน์อ้างอิงในตารางรายละเอียด |
| `หน่วยว่าง!BC` | END_GUARANTEE_DATE | สิ้นสุดค้ำประกัน |

| `หน่วยว่าง!BG` | REF_NO | อ้างถึง |

**สถานะ 4 แบบ** (มาจาก `AM` × `AU` ผสมกัน — ตรงกับ 4 คอลัมน์ COUNTIFS เดิมในสรุปหน่วยเต็ม `AD-AG`)

### 2.3 Sub-tab "การเปลี่ยนแปลง" — เทียบ MAT ระหว่างไฟล์เก่า/ใหม่ ⭐ใหม่

**หลักการ:** จับคู่ด้วย **MAT** ระหว่างชีต `หน่วยว่างเดิม` (snapshot ก่อนอัปเดต) กับข้อมูลชุดใหม่ (`หน่วยว่าง` + หน่วย Active ทั้ง 3 ชีตธุรกรรม) แบ่งผลเป็น 4 กลุ่ม:

| กลุ่ม | ความหมาย | เช็คจากไหน |
|---|---|---|
| 🟢 ยังว่างเหมือนเดิม | MAT อยู่ในหน่วยว่างทั้ง 2 ไฟล์ สถานะย่อยเหมือนเดิม | หน่วยว่าง(เก่า) ∩ หน่วยว่าง(ใหม่), status เท่ากัน |
| 🟡 ว่างเหมือนเดิมแต่เปลี่ยนสถานะย่อย | เช่น "ไม่พร้อมขาย" → "พร้อมขาย" | หน่วยว่าง(เก่า) ∩ หน่วยว่าง(ใหม่), status ต่างกัน |
| 🔵 เปลี่ยนเป็น Active แล้ว | MAT เดิมที่เคยว่าง ตอนนี้ไปโผล่ในมีสัญญา/เช่าเหมา/เช่าซื้อรอโอน | หน่วยว่าง(เก่า) ∩ หน่วย Active(ใหม่) — บอกได้ว่าไปเป็นสถานะไหน |
| ⚫ หาไม่เจอ | ไม่อยู่ทั้งหน่วยว่างและหน่วย Active ในไฟล์ใหม่ | อาจโอนกรรมสิทธิ์แล้ว/โครงการถูกลบ/ข้อมูลไม่ตรงกัน |

**ไม่เช็คกลุ่ม "ว่างใหม่"** (MAT ที่เพิ่งว่างในไฟล์ใหม่) เพราะดูได้จาก sub-tab "หน่วยว่างปัจจุบัน" อยู่แล้ว (ตามที่ตกลงกันไว้)

**กฎอนุรักษ์ตัวเลขที่ใช้ตรวจสอบ:**
1. 🟢 + 🟡 + 🔵 + ⚫ = จำนวนหน่วยว่างทั้งหมดในไฟล์**เก่า** (4,822)
2. 🟢 + 🟡 + ว่างใหม่ = จำนวนหน่วยว่างทั้งหมดในไฟล์**ใหม่** (2,637)

**ผลตรวจจริง (ไฟล์ปัจจุบัน):** ยังว่างเหมือนเดิม 2,635 / เปลี่ยนสถานะย่อย 1 / เปลี่ยนเป็น Active 22 (hire_purchase 20, pending_transfer 2) / หาไม่เจอ 2,164 (ในนี้ 2,162 คือโครงการไม่มีในไฟล์ปัจจุบันแล้ว, มีแค่ 2 รายที่โครงการยังอยู่แต่ MAT หายไปจริง) — สมการที่ 1: 2635+1+22+2164=4822 ✓ | สมการที่ 2: 2635+1+1(ว่างใหม่)=2637 ✓ — **ทั้ง 2 สมการลงตัวพอดี ไม่มีหน่วยตกหล่น**

ตรวจสอบเพิ่มเติม: ไม่มี MAT ซ้ำในทั้งชีตเก่าและชีตใหม่

### 2.4 กติกาการ join ที่ใช้ร่วมกันทุก tab

- ถ้ารหัสโครงการจากชีตธุรกรรมไม่มีอยู่ในชีต "สรุปหน่วยเต็ม" (185 โครงการ) → **ตัดทิ้ง** ไม่นำมาแสดง (ตรงพฤติกรรมเดิมของสูตร COUNTIFS ที่นับได้เฉพาะโครงการที่มีแถวอยู่ในสรุปหน่วยเต็มเท่านั้น) — ยกเว้น sub-tab "การเปลี่ยนแปลง" ที่ใช้ข้อมูลดิบจากชีต `หน่วยว่างเดิม` แบบไม่กรองโครงการออก (เพื่อให้เห็นกรณี "โครงการถูกลบไปแล้ว" ชัดเจน)
- ข้อมูลส่วนบุคคล (ชื่อลูกค้า/เลขบัตร ปชช./เบอร์โทร) **ตัดออกทั้งหมด** ทุก tab — เก็บเฉพาะ MAT/บ้านเลขที่/สถานะ/ค่าอ้างอิงที่จำเป็นสำหรับตรวจสอบยอด

### 2.5 การตรวจทานความถูกต้อง (ยืนยันด้วย Python, ไฟล์ปัจจุบัน)

| รายการ | ผลตรวจ |
|---|---|
| สูตร COUNTIFS ทั้ง 10 คอลัมน์ใน "สรุปหน่วยเต็ม" อ่านครบ 185 แถว รูปแบบเดียวกันทุกแถว | **ตรงกัน 100%** |
| หน่วย Active ที่ join ได้ (37,824 หน่วย) เทียบกับผลรวม `active_total` จาก Excel | **ตรงกัน 37,824 = 37,824** |
| หน่วยเช่าซื้อ (`hire_purchase`) รวม code 20+80 (12,672 หน่วย) เทียบกับผลรวมคอลัมน์ Y จาก Excel | **ตรงกัน 12,672 = 12,672** |
| หน่วยว่างใหม่ที่ join ได้ (2,637 หน่วย) เทียบกับผลรวม `vacant_total` จาก Excel | **ตรงกัน 2,637 = 2,637** |
| เปรียบเทียบหน่วยว่างเก่า-ใหม่ 4 กลุ่ม | **สมการอนุรักษ์ตัวเลขทั้ง 2 สมการลงตัว** (ดูหัวข้อ 2.3) |
| MAT ซ้ำในชีตหน่วยว่างเก่า/ใหม่ | **ไม่มี** |

## 3) สถาปัตยกรรมไฟล์ (เทคนิคบีบอัด)

ไฟล์เดียวจบ ไม่มีไฟล์แยก ไม่มี backend ใช้เทคนิค **gzip + base64** ฝังข้อมูลเป็นตัวแปร JS:

```
ขั้นตอนตอนสร้างไฟล์ (ทำครั้งเดียว, ฝั่ง Python):
1. แปลงแต่ละแถวเป็น array (ไม่ใช่ object ซ้ำคีย์) → {cols:[...], rows:[[...],[...]]}
2. JSON.dumps แบบไม่มีช่องว่าง (separators=(',',':'))
3. gzip compress (level 9)
4. base64 encode → เก็บในตัวแปร JS

ขั้นตอนตอนเปิดไฟล์ (ฝั่งเบราว์เซอร์):
Base64 → atob() → DecompressionStream('gzip') (Web API มาตรฐาน ไม่ต้องใช้ไลบรารีเพิ่ม)
→ JSON.parse → คืนรูป array-of-objects ด้วย cols mapping
```

| ตัวแปร | เนื้อหา | โหลดตอนไหน | ขนาด (บีบอัดแล้ว) |
|---|---|---|---|
| `DB64` | 185 โครงการ × 38 คอลัมน์ (ระดับโครงการ) | ตอนเปิดไฟล์ (ทุก tab ใช้) | ~10.3 KB |
| `PB64` | 40,461 รายการระดับหน่วย (หน่วย Active 37,824 + หน่วยว่างใหม่ 2,637) | ตอนเปิดไฟล์ | ~255 KB |
| `CS64` | มีสัญญา: MAT → CUST_STATUS_NAME + CONTRACT_TYPE_CODE จริง (17,466 แถว, 3 คอลัมน์) | ตอนเปิดไฟล์ | ~61 KB |
| `PF64` | เช่าซื้อรอโอน: MAT → PAY_FR (8,562 แถว) | ตอนเปิดไฟล์ | ~32 KB |
| `VC64` | หน่วยว่างใหม่: คอลัมน์เพิ่มเติม (CONTRACT_STATUS ฯลฯ) 2,637 แถว | ตอนเปิดไฟล์ | ~28 KB |
| `CH64` | ผลเปรียบเทียบหน่วยว่างเก่า-ใหม่ 4,822 แถว (ใช้ใน sub-tab "การเปลี่ยนแปลง") | ตอนเปิดไฟล์ | ~16 KB |

**หมายเหตุ:** ทุกก้อนข้อมูลโหลดพร้อมกันตอนเปิดไฟล์แล้ว (ขนาดรวมยังเล็กมาก) ส่วน "การประมวลผล" (join กับ RAW_DATA, สร้างตาราง/กราฟ) ของแต่ละ tab/sub-tab ยัง **lazy อยู่เหมือนเดิม** (ทำงานเฉพาะตอนคลิกเข้า tab/sub-tab นั้นครั้งแรก)

**ไลบรารีที่ฝังในไฟล์ (inline, ไม่มี CDN ภายนอก):** Chart.js (UMD) + SheetJS `xlsx.mini.min.js`

**ข้อกำหนดเบราว์เซอร์:** ต้องรองรับ `DecompressionStream` (Chrome/Edge 80+, Firefox 113+, Safari 16.4+)

## 5) หลักการออกแบบที่ใช้ร่วมกันทุก tab

- **Cross-filter ไม่กรองตัวเอง**: dropdown แต่ละตัวคำนวณตัวเลือกจากตัวกรองอื่นที่เลือกไว้ทั้งหมด ไม่รวมค่าที่ตัวเองเลือกอยู่
- **การ์ด KPI = ตัวกรองในตัว**: คลิกการ์ดหรือ badge ใดก็ตามจะกรองทั้งหน้า (กราฟ+ตาราง) ตามนั้นทันที มีกรอบไฮไลต์สีของตัวเองบอกสถานะ + chip โผล่ในแถบตัวกรอง
- **ตารางสรุประดับ กอง → โครงการ**: ทุก tab/sub-tab ที่เป็นระดับหน่วย ใช้รูปแบบเดียวกัน (1 แถว = 1 โครงการ ไม่ใช่ 1 สำนักงาน) เพราะรู้จำนวนหน่วยต่อโครงการได้ตรงประเด็นกว่า
- **Lazy processing**: tab/sub-tab ที่ยังไม่เคยคลิกเข้าจะยังไม่ join/ประมวลผลข้อมูล (ข้อมูลดิบโหลดพร้อมกันหมดตอนเปิดไฟล์ แต่การประมวลผลจริงรอจนกว่าจะคลิกเข้า)
- **Pagination สำหรับตารางที่มีข้อมูลเยอะ**: ตารางรายละเอียดของ tab หน่วย Active, หน่วยว่าง, และ sub-tab การเปลี่ยนแปลง แสดงทีละ 300 แถว ป้องกันเบราว์เซอร์ค้าง — export ยังคงได้ข้อมูลเต็มเสมอ
- **Export แยกอิสระต่อตาราง**: ทุกตารางสรุป/รายละเอียด ในทุก tab มีปุ่ม PDF (แดง) / Excel (เขียว) ของตัวเอง

## 6) ประวัติการพัฒนา (สรุปย่อ)

1. สร้างแดชบอร์ดเริ่มต้น (การ์ด/ฟิลเตอร์/กราฟ/ตาราง/export) — เฉพาะ tab ภาพรวม
2. แก้บั๊กกราฟว่างเปล่า → ฝังไลบรารีในไฟล์ทั้งหมด, ปรับตารางสรุปเป็น group by กอง
3-7. ปรับ UI หลายรอบ (KPI 4 การ์ด, breakdown, audit drill-down, บีบอัด gzip+base64, ตัดคำสำนักงานในกราฟ, cross-filter, การ์ดคลิกกรองได้) พร้อม**ตรวจสอบสูตร COUNTIFS ทั้งหมดอย่างละเอียด** พบช่องว่าง `CONTRACT_TYPE_CODE=80` ที่ตกหล่นจากสูตรเดิม
8-10. สร้าง **tab "หน่วย Active"** (join 3 ชีต, ตรวจนับยืนยัน 36,220 หน่วย), แก้ปัญหาเบราว์เซอร์ค้าง → เพิ่ม pagination, ปรับการ์ด KPI เป็น 7 การ์ดแยกกัน
11-12. สร้าง **tab "หน่วยว่าง"** (join ชีตหน่วยว่าง+คอลัมน์เพิ่ม, ตรวจนับยืนยัน 2,660 หน่วย), ปรับสี PDF export, ปรับตัดคำแล้วยกเลิก (กินกระดาษเกิน)
13-14. เพิ่มตัวกรอง "สำนักงาน"+"ชื่อโครงการ" ทุก tab, ปรับตารางสรุปเป็น "กอง → โครงการ" (ถอด "จำนวนโครงการ" ออก) ทั้ง Active และ หน่วยว่าง
15-16. เพิ่มคอลัมน์ CONTRACT_TYPE_CODE (derive จาก status ตอนนั้น), **แก้บั๊ก CUST_STATUS_NAME ว่างเปล่า** — พบว่า AUDIT_DATA เดิมไม่เคยเก็บค่านี้จากชีตมีสัญญา ดึงใหม่เป็น `CS64` (ดูหัวข้อ 9)
17. เพิ่มคอลัมน์ **PAY_FR** จากชีตเช่าซื้อรอโอน (ข้อมูลใหม่ ไม่เคยฝังไว้ก่อน) + ทำเป็นตัวกรองได้ด้วย
18. เพิ่มตัวกรอง **"การซื้อคืน"** และ **"หมายเหตุ"** ใน tab หน่วยว่าง (derive จาก REDATE/STOCK_RMK)
19. วางแผน sub-tab **"การเปลี่ยนแปลงหน่วยว่าง"** ร่วมกัน (จับคู่ MAT, 4 กลุ่ม, กฎอนุรักษ์ตัวเลข 2 สมการ, ตำแหน่ง UI เป็น sub-tab ซ้อนใน "หน่วยว่าง")
20. **ได้ไฟล์ Excel ฉบับใหม่ (เพิ่มชีต `หน่วยว่างเดิม` + code 80)** — พบสูตรเช่าซื้อพิมพ์ผิด (`O="50"` ซ้ำ แทนที่จะเป็น `O="80"`) แจ้งกลับก่อนดำเนินการ ได้ไฟล์แก้ไขแล้วส่งมาใหม่ → **rebuild ข้อมูลทั้งหมด** (DB64/PB64/CS64/PF64/VC64) จากไฟล์ล่าสุด + สร้าง **CH64** (ข้อมูลเปรียบเทียบ) + สร้าง sub-tab "การเปลี่ยนแปลง" ตามแผน — ตรวจนับยืนยันครบทุกจุด (ดูหัวข้อ 2.5) code 80 รวมเข้ากับ "(3)เช่าซื้อ" แล้ว หน่วย Active รวมเพิ่มจาก 36,220 → 37,824

## 7) หลักการสำคัญที่ยึดตลอดโปรเจกต์

- **ไม่เชื่อสูตร/ตัวเลขจากผู้ใช้หรือไฟล์ตรงๆ โดยไม่ตรวจสอบ** — ทุกครั้งที่ได้สูตรหรือไฟล์ใหม่ จะอ่านสูตรจริงในไฟล์เทียบกับที่บอกไว้ก่อนเสมอ (เจอมาแล้ว 1 ครั้งที่สูตรพิมพ์ผิดจากที่ตั้งใจ)
- **ทุกยอดรวมต้อง "อนุรักษ์" ลงตัว 100%** — ผลรวมของทุกกลุ่มย่อยต้องเท่ากับยอดรวมทั้งหมดเป๊ะ ถ้าไม่ลงตัวคือมีบั๊กต้องหาให้เจอก่อนส่งมอบ
- **ข้อมูลที่ไม่เคยฝังไว้ในไฟล์ ต้องดึงใหม่จาก Excel ต้นฉบับเสมอ** — ห้ามสมมติว่า field มีอยู่แล้วจากฟีเจอร์เก่าโดยไม่ตรวจสอบก่อน (บทเรียนจากบั๊ก CUST_STATUS_NAME)
- **ตัด PII ทุกจุด** ไม่มีชื่อ/เลขบัตร/เบอร์โทรลูกค้าฝังอยู่ในไฟล์เลย
