# แดชบอร์ดหน่วยความรับผิดชอบ — การเคหะแห่งชาติ

เอกสารนี้สรุปโครงการแดชบอร์ดทั้งหมด เผื่อไว้สำหรับเปิดแชทใหม่แล้วอ้างอิงต่อได้ทันที

---

## 1) ภาพรวมโครงการ

แดชบอร์ดแบบ **ไฟล์ HTML เดียว** (single-file, ไม่มี backend, ไม่ต้องเชื่อมอินเทอร์เน็ต) มี **3 tab หลัก** และ **1 sub-tab ซ้อนอยู่ใน tab หน่วยว่าง**:

| Tab | เนื้อหา | ระดับข้อมูล |
|---|---|---|
| **ภาพรวม** | สรุปทุกโครงการจากชีต "สรุปหน่วยเต็ม" | ระดับโครงการ (185 แถว) |
| **หน่วย Active** | หน่วยที่มีสัญญา/เช่าเหมา/รอโอน จาก 3 ชีตธุรกรรม | ระดับหน่วย/MAT (37,824 แถว) |
| **หน่วยว่าง** ▸ หน่วยว่างปัจจุบัน | หน่วยว่างจากชีต "หน่วยว่าง" | ระดับหน่วย/MAT (2,595 แถว) |
| **หน่วยว่าง** ▸ การเปลี่ยนแปลง | เทียบหน่วยว่างเก่ากับข้อมูลชุดใหม่ (MAT) — 5 กลุ่ม | ระดับหน่วย/MAT (4,823 แถว รวมกลุ่ม "ว่างใหม่") |

**ไฟล์ล่าสุด:** `LAA_Dashboard_หน่วยความรับผิดชอบ.html` (~1.19MB)

สร้างจากไฟล์ Excel `DBหน่วยความรับผิดชอบ.xlsx` ซึ่งมี **7 ชีต**:

| ชีต | หน้าที่ | จำนวนแถว |
|---|---|---|
| `อธิบาย` | หมายเหตุ SQL query ต้นทาง (คอลัมน์ B บอกชื่อชีตปลายทาง) | 29 |
| **`สรุปหน่วยเต็ม`** | **ชีตหลักระดับโครงการ** ใช้เป็น context และเป็น **ขอบเขตหลักของทั้งระบบ (185 โครงการ)** | 185 |
| `หน่วยว่าง` | ข้อมูลระดับหน่วย (ชุดล่าสุด — ปรับ SQL ใหม่แล้ว ดูหัวข้อ 1.1) ใช้ทำ sub-tab "หน่วยว่างปัจจุบัน" | 2,794 |
| `หน่วยว่างเดิม` | Snapshot ของชีต "หน่วยว่าง" **ก่อน**อัปเดตล่าสุด ใช้เทียบความเปลี่ยนแปลงใน sub-tab "การเปลี่ยนแปลง" | 4,822 |
| `เช่าซื้อรอโอน` | ข้อมูลระดับหน่วย ใช้ทำสถานะ "ติดค้ำประกันฯ/รอโอน" ใน tab "หน่วย Active" | 8,567 |
| `มีสัญญา` | ข้อมูลระดับหน่วย ใช้ทำสถานะ "เช่า/เช่าซื้อ/จะซื้อจะขาย" ใน tab "หน่วย Active" | 17,845 |
| `เช่าเหมา` | ข้อมูลระดับหน่วย ใช้ทำสถานะ "เช่าเหมา" ใน tab "หน่วย Active" | 11,796 |

### 1.1 หลักการที่ยึดตลอดทั้งระบบ: "185 โครงการ" คือขอบเขตเดียว

ชีต "สรุปหน่วยเต็ม" (185 โครงการ) เป็น **single source of truth** ของขอบเขตทั้งแดชบอร์ด — ไม่ว่าชีตธุรกรรม (มีสัญญา/เช่าเหมา/เช่าซื้อรอโอน/หน่วยว่าง/หน่วยว่างเดิม) จะมีข้อมูลดิบมากแค่ไหน หรือ SQL ต้นทางจะถูกปรับเงื่อนไขอย่างไร (เช่น ตัดเงื่อนไข "ก่อสร้างแล้วเสร็จ/ส่งมอบโครงการ" ออก ทำให้ "หน่วยว่าง" ลดจาก 2,637 เหลือ 2,595 หน่วยในไฟล์ล่าสุด) **โครงการที่ไม่อยู่ใน 185 นี้จะถูกตัดออกจากทุกจุดของแดชบอร์ดเสมอ** ทั้ง tab ภาพรวม, หน่วย Active, หน่วยว่างปัจจุบัน, และ sub-tab การเปลี่ยนแปลง

ข้อดี: แก้ SQL ต้นทางกี่รอบ ปรับเงื่อนไขกี่แบบ ก็แค่ rebuild ข้อมูลจากไฟล์ใหม่ **ไม่ต้องแก้โค้ดแดชบอร์ดเลย** เพราะ join logic ทุกจุดอ้างอิงขอบเขตจากสรุปหน่วยเต็มเป็นจุดเดียวอยู่แล้ว — ทุกการ์ด KPI (ทั้งการ์ดรวมและการ์ดสถานะย่อย) มี badge บอก **"พบใน X โครงการ จาก 185 โครงการทั้งหมด"** ให้เห็นการล็อกขอบเขตนี้บนหน้าจอโดยตรง ไม่ต้องเดา

## 2) หลักการ Join ข้อมูลข้ามชีต (สำคัญที่สุด)

**หลักการทำงาน:** ชีต "สรุปหน่วยเต็ม" มีสูตร `COUNTIFS` ฝังไว้ในคอลัมน์สถานะหน่วย (W-AG) ที่ดึงยอดนับจาก 4 ชีตธุรกรรม โดยแต่ละสูตรมีเงื่อนไข **ไม่เหมือนกัน** ทั้ง join key และเงื่อนไขกรอง — วิธีสร้างแต่ละ tab คือ **อ่านสูตร COUNTIFS จริงในไฟล์แล้วแปลงกลับเป็นตรรกะ join/filter ในโค้ด JS** (ไม่เชื่อคำอธิบายปากเปล่าตรงๆ โดยไม่ตรวจสอบไฟล์จริงก่อน — เคยเจอ 1 ครั้งที่สูตรพิมพ์ผิดจากที่ตั้งใจ) ค่าตัวเลขระดับโครงการ (`DB64`) อ่านจากผลลัพธ์ที่ Excel คำนวณไว้แล้วโดยตรง (`data_only=True`) ไม่ recompute เองใน Python

### 2.1 Tab "หน่วย Active" — join 3 ชีต

| สถานะ | ชีตต้นทาง | join key | เงื่อนไข |
|---|---|---|---|
| (1) เช่า | `มีสัญญา` | คอลัมน์ `D` (PROJ) | `O` (CONTRACT_TYPE_CODE) = `"50"` |
| (2) เช่าเหมา | `เช่าเหมา` | คอลัมน์ `E` | ไม่มีเงื่อนไขสถานะ |
| (3) เช่าซื้อ | `มีสัญญา` | คอลัมน์ `D` | `O` = `"20"` **OR** `O` = `"80"` |
| (4) จะซื้อจะขาย | `มีสัญญา` | คอลัมน์ `D` | `O` = `"10"` **AND** `Y` = `"กำลังผ่อนชำระ"` |
| (5) ติดค้ำประกันฯ | `เช่าซื้อรอโอน` | คอลัมน์ `F` | `V` มีคำว่า `"ค้ำประกัน"` |
| (6) รอโอน | `เช่าซื้อรอโอน` | คอลัมน์ `F` | `V` มีคำว่า `"รอโอน"` |

**ประวัติการแก้ไขสูตร "(3)เช่าซื้อ" (ปิดแล้ว):** รอบแรกไฟล์ยังไม่มี code 80 → รอบสองสูตรพิมพ์ผิดเป็น `O="50"` ซ้ำ (ตรวจพบและแจ้งกลับก่อนใช้งาน) → รอบสามแก้เป็น `O="80"` ถูกต้องแล้ว ตรวจสอบยืนยันครบ 185 แถว

คอลัมน์ที่ดึงมาใช้ต่อ 1 หน่วย: `MAT`, บ้านเลขที่, `CONTRACT_TYPE_CODE` จริง (เก็บแยกต่อหน่วย ไม่ derive จาก status เพราะ "(3)เช่าซื้อ" ครอบคลุม 2 code แล้ว), สถานะ, ค่าอ้างอิง (`CUST_STATUS_NAME`/`CONTRACT_STATUS` แล้วแต่แหล่ง), `PAY_FR` (เฉพาะแหล่งเช่าซื้อรอโอน)

### 2.2 Tab "หน่วยว่าง" (sub-tab ปัจจุบัน) — join 1 ชีต

| ที่มา | คอลัมน์ | ใช้เป็น |
|---|---|---|
| `หน่วยว่าง!O` | PROJ_CODE | join key |
| `หน่วยว่าง!Q` | CL_MATERIAL_NO | MAT |
| `หน่วยว่าง!W` | HOUSE_NO_ACT | บ้านเลขที่ |
| `หน่วยว่าง!AM`×`AU` | STOCK_STATUS × TYPE_NAME | 4 สถานะ (ว่างพร้อม/ไม่พร้อมขาย × เพื่อเช่า/เพื่อขาย) |
| `หน่วยว่าง!AU` | TYPE_NAME | ใช้ซ้ำเป็น **"รูปแบบหารายได้" ระดับหน่วย** (แทนค่าระดับโครงการ) |
| `หน่วยว่าง!BB,BC,BD,BE,BF,BG` | CONTRACT_STATUS, END_GUARANTEE_DATE, REDATE, DATEK, STOCK_RMK, REF_NO | คอลัมน์อ้างอิง + ใช้ derive ตัวกรอง **"การซื้อคืน"** (จาก REDATE) และ **"หมายเหตุ"** (จาก STOCK_RMK ตรงๆ มีแค่ ~12 ค่าคงที่) |

### 2.3 Sub-tab "การเปลี่ยนแปลง" — เทียบ MAT ระหว่างไฟล์เก่า/ใหม่ — 5 กลุ่ม

จับคู่ด้วย **MAT** ระหว่างชีต `หน่วยว่างเดิม` (baseline) กับข้อมูลชุดใหม่ (`หน่วยว่าง` + หน่วย Active ทั้ง 3 ชีต):

| กลุ่ม | สี | ความหมาย | เช็คจากไหน |
|---|---|---|---|
| 🟢 ยังว่างเหมือนเดิม | เขียว | MAT อยู่ในหน่วยว่างทั้ง 2 ไฟล์ สถานะย่อยเท่ากัน | เก่า ∩ ใหม่, status เท่ากัน |
| 🟡 ว่างเหมือนเดิมแต่เปลี่ยนสถานะย่อย | ทอง | เช่น "ไม่พร้อมขาย"→"พร้อมขาย" | เก่า ∩ ใหม่, status ต่างกัน |
| 🔵 เปลี่ยนเป็น Active แล้ว | เขียวมิ้นท์ | MAT เดิมไปโผล่ในหน่วย Active | เก่า ∩ Active(ใหม่) |
| ⚫ หาไม่เจอ | แดง | ไม่อยู่ทั้งหน่วยว่างและ Active ในไฟล์ใหม่ | เก่า − (ใหม่ ∪ Active) |
| 🟣 ว่างใหม่ ⭐ | ม่วง | MAT ที่เพิ่งว่างในไฟล์ใหม่ ไม่เคยอยู่ในหน่วยว่างเดิมเลย | ใหม่ − เก่า |

**กฎอนุรักษ์ตัวเลข 2 สมการ:**
1. 🟢 + 🟡 + 🔵 + ⚫ = จำนวนหน่วยว่างทั้งหมดในไฟล์**เก่า** (4,822 — ก่อนล็อก 185 โครงการ)
2. 🟢 + 🟡 + 🟣 = จำนวนหน่วยว่างทั้งหมดในไฟล์**ใหม่** (2,595)

**ผลตรวจจริง (ไฟล์ล่าสุด, หลังล็อก 185 โครงการ):** 🟢2,594 / 🟡0 / 🔵23 (hire_purchase 20, pending_transfer 2, rent 1) / ⚫43 / 🟣1 — รวม 2,661 หน่วย (จากทั้งหมด 4,823 ก่อนล็อก) — สมการทั้ง 2 ลงตัวพอดี ไม่มีหน่วยตกหล่นทั้ง 2 ฝั่ง ไม่มี MAT ซ้ำ

**หมายเหตุกลุ่ม ⚫ หาไม่เจอ:** ก่อนล็อก 185 โครงการมี 2,205 หน่วย ในนี้ 2,162 หน่วยเป็นเพราะ**โครงการนั้นไม่มีอยู่ในสรุปหน่วยเต็มฉบับปัจจุบันแล้ว** (ระหว่างพัฒนาเคยตัดกลุ่มนี้ออกทั้งหมดตามหลักการข้อ 1.1 — เหลือเฉพาะ ~43 หน่วยที่โครงการยังอยู่จริงแต่ MAT หายไป) — ผู้ใช้ยืนยันว่าตรงกับความเป็นจริงเรื่อง "โครงการที่ยังไม่แบ่งความรับผิดชอบ"

**ไม่กรองโครงการออกจากฝั่ง `หน่วยว่างเดิม`/`ว่างใหม่` ก่อนเทียบ** — ใช้ข้อมูลดิบทั้งหมดเทียบกันก่อน แล้วค่อยกรองผลลัพธ์สุดท้ายด้วย 185 โครงการปัจจุบันทีเดียว (ไม่ใช่กรองตั้งแต่ต้นทาง) เพื่อให้เห็นภาพ "โครงการหายไปจากระบบ" ได้ถูกต้อง

### 2.4 การตรวจทานความถูกต้อง (ยืนยันด้วย Python ทุกไฟล์ที่ได้รับ)

ทุกครั้งที่ได้ไฟล์ใหม่: อ่านสูตร COUNTIFS จริงเทียบกับที่คาดไว้ → ดึงข้อมูลระดับหน่วย → เทียบผลรวมกับตัวเลขที่ Excel คำนวณให้แล้ว ต้อง**ตรงกัน 100% ทุกจุด** ก่อนส่งมอบเสมอ (ไม่เคยมีกรณีตัวเลขไม่ลงตัวหลุดไปถึงมือผู้ใช้)

## 3) สถาปัตยกรรมไฟล์ (เทคนิคบีบอัด)

ใช้ **gzip + base64** ฝังข้อมูลเป็นตัวแปร JS ในไฟล์เดียว ถอดรหัสฝั่งเบราว์เซอร์ด้วย `DecompressionStream('gzip')` (Web API มาตรฐาน)

| ตัวแปร | เนื้อหา | ขนาด (บีบอัดแล้ว) |
|---|---|---|
| `DB64` | 185 โครงการ × 38 คอลัมน์ | ~10.2 KB |
| `PB64` | 40,419 รายการระดับหน่วย (หน่วย Active 37,824 + หน่วยว่างใหม่ 2,595) | ~254 KB |
| `CS64` | มีสัญญา: MAT → CUST_STATUS_NAME + CONTRACT_TYPE_CODE จริง (17,466 แถว) | ~61 KB |
| `PF64` | เช่าซื้อรอโอน: MAT → PAY_FR (8,562 แถว) | ~32 KB |
| `VC64` | หน่วยว่างใหม่: คอลัมน์เพิ่มเติม (2,595 แถว) | ~27 KB |
| `CH64` | ผลเปรียบเทียบหน่วยว่างเก่า-ใหม่ **5 กลุ่ม** (4,823 แถว) | ~16 KB |

ทุกก้อนโหลดพร้อมกันตอนเปิดไฟล์ (ขนาดรวมเล็ก) ส่วน "การประมวลผล" ของแต่ละ tab/sub-tab ยัง **lazy** (ทำงานเฉพาะตอนคลิกเข้าครั้งแรก)

**ไลบรารีที่ฝังในไฟล์:** Chart.js (UMD) + SheetJS `xlsx.mini.min.js` — ไม่มี CDN ภายนอก

## 4) ฟีเจอร์ในแดชบอร์ด

### 4.1 หลักการ UI ที่ใช้ร่วมกันทุก tab/sub-tab

- **แถบสลับ tab หลัก** `[ภาพรวม] [หน่วย Active] [หน่วยว่าง]` — ปุ่มลอยทรงมน (pill) พื้นน้ำเงินไล่เฉด+ตัวหนังสือขาวเมื่อเลือกอยู่ เด่นชัดจากพื้นขาวของปุ่มอื่น
- **แถบสลับ sub-tab** ใน "หน่วยว่าง" `[หน่วยว่างปัจจุบัน] [การเปลี่ยนแปลง]` — ปุ่มทรงเดียวกันแต่ใช้โทนทอง (แยกระดับจาก tab หลักที่เป็นน้ำเงิน)
- **การ์ด KPI = ตัวกรองในตัว**: คลิกการ์ด (หรือ badge ย่อยใน tab ภาพรวม) กรองกราฟ/ตารางด้านล่างทันที มีกรอบไฮไลต์สีของตัวเอง
- **การ์ด "รวม" (hero) แสดงตามสิ่งที่กำลังแสดงจริงเสมอ** ไม่ว่าจะกรองผ่าน dropdown หรือคลิกการ์ดสถานะก็ตาม (แก้บั๊กไปแล้ว — ดูหัวข้อ 5) ส่วน % ของการ์ดย่อยยังคำนวณจากยอดรวมทั้งหมดเสมอ (ไม่เพี้ยนเป็น 100%)
- **ทุกการ์ด (รวม+ย่อย) มี badge "พบใน X โครงการ จาก 185 โครงการทั้งหมด"** คำนวณสดจากข้อมูลของการ์ดนั้นๆ เอง เสมอ ไม่ต้องรอคลิกก็ถูกต้องอยู่แล้ว
- **Cross-filter ไม่กรองตัวเอง**, **ตารางสรุประดับ กอง→โครงการ**, **Pagination หน้าละ 300 แถว** สำหรับตารางรายละเอียดที่มีข้อมูลเยอะ, **Export PDF/Excel แยกอิสระทุกตาราง**

### 4.2 Tab "ภาพรวม" — การ์ด 4 ใบ + badge ย่อยในตัว, ตัวกรอง 8 ตัว, ตาราง 2 แบบ
### 4.3 Tab "หน่วย Active" — การ์ด 7 ใบสีต่างกันทุกใบ, ตัวกรอง 6 ตัว (รวม PAY_FR), รายละเอียด 37,824 แถว
### 4.4 Tab "หน่วยว่าง" ▸ หน่วยว่างปัจจุบัน — การ์ด 5 ใบ, ตัวกรอง 7 ตัว (รวมการซื้อคืน/หมายเหตุ)
### 4.5 Tab "หน่วยว่าง" ▸ การเปลี่ยนแปลง — การ์ด 6 ใบ (รวม+5กลุ่ม), ตัวกรอง 5 ตัว, timeline วงจรชีวิตหน่วยว่างครบวงจร

## 5) บั๊กสำคัญที่เจอและแก้แล้ว

### 5.1 CUST_STATUS_NAME ว่างเปล่า (tab หน่วย Active)
**สาเหตุ:** `AUDIT_DATA` ชุดเดิม (ทำไว้ตั้งแต่ก่อนเริ่มโปรเจกต์ tab นี้) ไม่เคยเก็บค่านี้จากชีต `มีสัญญา` (เก็บเฉพาะเช่าซื้อรอโอน/หน่วยว่าง) **แก้:** ดึงค่าจริงจากชีตมีสัญญาใหม่ทั้งหมดเป็น `CS64`

### 5.2 การ์ด "รวม" ไม่เปลี่ยนตามการคลิกการ์ดสถานะ (ทุก tab ระดับหน่วย)
**อาการ:** dropdown filter เปลี่ยนตัวเลขการ์ดรวมได้ แต่คลิกการ์ดสถานะ (เช่น "(4)จะซื้อจะขาย" กรองเหลือ 1 หน่วย) การ์ดรวมยังค้างที่ยอดเดิม ไม่ตรงกับตารางที่กรองแล้ว
**สาเหตุ:** ออกแบบไว้ให้การ์ดรวมอ่านค่าจาก `base` (กรองด้วย dropdown เท่านั้น) ไม่ได้รวม status filter จากการคลิกการ์ดเข้าไปด้วย
**แก้:** แยกตัวแปร `grandTotal` (ใช้เป็นตัวหาร % ของการ์ดย่อย ไม่เปลี่ยนตามสถานะที่เลือก) ออกจาก `heroValue`/`rows` (ค่าที่การ์ดรวมแสดงจริง = สิ่งที่กำลังแสดงในตาราง รวม status filter ด้วย) แก้ครบทั้ง 3 จุด: tab หน่วย Active, หน่วยว่างปัจจุบัน, sub-tab การเปลี่ยนแปลง — ตรวจสอบด้วยการจำลองคลิกจริงผ่าน Node.js + jsdom ยืนยันผลถูกต้องก่อนส่งมอบ

**บทเรียน:** เวลาต่อยอด/reuse ข้อมูลจากฟีเจอร์เก่า ต้องเช็คให้ดีว่าฟิลด์ที่จะใช้ครอบคลุมทุก source จริงหรือไม่ และเวลาออกแบบ "การ์ดรวม" ต้องตัดสินใจให้ชัดว่าจะสะท้อน filter ระดับไหนบ้าง แล้วทำให้สอดคล้องกันทุกจุดที่ผู้ใช้จะโต้ตอบด้วย (dropdown, การ์ด, badge ย่อย) ไม่ให้มีจุดไหนหลุด

### 5.3 ปุ่ม "ล้างตัวกรอง" ใน tab ภาพรวม ไม่รีเซ็ตกราฟ (ทำงานไม่สมบูรณ์)
**อาการ:** กด "ล้างตัวกรอง" แล้ว dropdown ทุกตัวว่างถูกต้อง แต่ถ้าเคยคลิกการ์ด/badge เลือก metric ไว้ก่อนหน้า (เช่น "(3)เช่าซื้อ") กราฟโดนัท/อันดับ และการไฮไลต์การ์ด ยังค้างอยู่ที่ metric เดิม ไม่กลับเป็น "หน่วยเต็ม"
**สาเหตุ:** ปุ่ม reset ของ tab ภาพรวม (`btnReset`) เขียนไว้ตั้งแต่รอบแรกสุดของโปรเจกต์ ก่อนจะมี metric ตัวเลือกจากการคลิกการ์ด — ตอนเพิ่มฟีเจอร์การ์ดคลิกกรองทีหลัง ลืมย้อนกลับมาอัปเดตปุ่มนี้ให้รีเซ็ต `selectedMetric`/`kpiFilterOn` ด้วย (สังเกตว่า tab หน่วย Active/หน่วยว่าง/การเปลี่ยนแปลง ที่สร้างทีหลังไม่มีปัญหานี้ เพราะออกแบบปุ่ม reset ให้ครบตั้งแต่ต้น)
**แก้:** เพิ่ม `selectedMetric = 'total'; kpiFilterOn = false;` ในปุ่ม reset ของ tab ภาพรวม ตรวจสอบด้วยการจำลองคลิกจริงผ่าน Node.js + jsdom ยืนยันว่า resultCount และการไฮไลต์การ์ดกลับสู่ค่าเริ่มต้นถูกต้องหลังกด reset

**บทเรียนเพิ่มเติม:** เวลาเพิ่มฟีเจอร์ใหม่ที่มี state ของตัวเอง (เช่น selectedMetric) ต้องไล่เช็คทุกจุดที่ "ควรจะรีเซ็ต" state นั้น ไม่ใช่แค่จุดที่สร้าง state — ปุ่ม reset ที่เขียนไว้ก่อนหน้าฟีเจอร์ใหม่จะไม่รู้จัก state ใหม่โดยอัตโนมัติ

## 6) หลักการสำคัญที่ยึดตลอดโปรเจกต์

- **ไม่เชื่อสูตร/ตัวเลขจากผู้ใช้หรือไฟล์ตรงๆ โดยไม่ตรวจสอบ** — อ่านสูตรจริงในไฟล์เทียบกับที่บอกไว้เสมอ
- **ทุกยอดรวมต้อง "อนุรักษ์" ลงตัว 100%** — ผลรวมย่อยต้องเท่ากับยอดรวมทั้งหมดเป๊ะ
- **ข้อมูลที่ไม่เคยฝังไว้ในไฟล์ ต้องดึงใหม่จาก Excel ต้นฉบับเสมอ** ห้ามสมมติว่ามีอยู่แล้ว
- **185 โครงการจากสรุปหน่วยเต็ม คือขอบเขตเดียวของทั้งระบบ** ไม่ว่า SQL ต้นทางจะเปลี่ยนแค่ไหน
- **ก่อนส่งมอบ UI ที่มีการโต้ตอบ (คลิก/กรอง) ทดสอบจำลองการคลิกจริงด้วยโปรแกรม** (Node.js + jsdom) ไม่ใช่แค่ตรวจ syntax เฉยๆ
- **ตัด PII ทุกจุด** ไม่มีชื่อ/เลขบัตร/เบอร์โทรลูกค้าฝังอยู่ในไฟล์เลย
